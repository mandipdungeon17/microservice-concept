## 1. History

### RestTemplate (Spring 3.0, 2009)

Spring's original imperative HTTP client. You write the URL, the method, the headers, the body serialization, and the response mapping — all by hand, per call.

```java
// RestTemplate — every call is manual plumbing
ResponseEntity<ProductResponse> resp = restTemplate.exchange(
    "http://PRODUCT-SERVICE/api/products/" + id,
    HttpMethod.GET,
    HttpEntity.EMPTY,
    ProductResponse.class
);
return resp.getBody();
```

Problems:

- URL strings are hardcoded. A typo compiles fine.
- No type safety between caller and callee. Rename an endpoint — the compiler doesn't tell you.
- Error handling must be wired manually per call.
- Load balancer integration requires wrapping with `@LoadBalanced` RestTemplate bean.

### Netflix Feign (2012, open-sourced 2013)

Invented at Netflix alongside Eureka and Ribbon. The core insight: **an HTTP API is a contract, and the same Java interface mechanism that defines local contracts can define remote contracts across services.**

Netflix used this internally at massive scale. Feign generates the HTTP implementation at startup from the annotated interface. You declare what, not how.

### Spring Cloud OpenFeign (~2015)

Spring Cloud wrapped Netflix Feign and replaced Netflix's annotations with Spring MVC annotations (`@GetMapping`, `@PathVariable`, `@RequestBody`, etc.). It also wired in Spring's Jackson encoder/decoder, Eureka load balancer, and error handling infrastructure.

`@EnableFeignClients` triggers the entire startup wiring pipeline.

## 2. What @FeignClient Actually Generates

When you annotate an interface with `@FeignClient`:

```java
@FeignClient(name = "PRODUCT-SERVICE")
public interface ProductFeignClient {
    @GetMapping("/api/products/{id}")
    ProductDTO getProductById(@PathVariable("id") Long id);
}
```

There is **no implementation class written by you or generated by a code generator**. What happens instead:

1. At startup, Spring creates a **JDK Dynamic Proxy** that implements `ProductFeignClient`.
2. The proxy holds an `InvocationHandler` (specifically, `FeignInvocationHandler`).
3. Any call to `productFeignClient.getProductById(42L)` routes through `FeignInvocationHandler.invoke()`.
4. The handler translates the method call into an HTTP request and returns the deserialized response.

This is the same mechanism behind `@Transactional` proxies, `@Cacheable` proxies, and Spring's JPA repository proxies — a proxy is injected in place of the "real" object, intercepting calls.

## 3. Startup Flow

Step-by-step when `PortfolioServiceApplication` starts with `@EnableFeignClients(basePackages = {"com.equitycart.commons.feign", "com.equitycart.portfolio.feign"})`:

```
@EnableFeignClients annotation
        │
        ▼
FeignClientsRegistrar (ImportBeanDefinitionRegistrar)
  — scans the specified basePackages
  — finds all interfaces annotated with @FeignClient
        │
        ▼
For each @FeignClient interface:
  Registers a FeignClientFactoryBean as a BeanDefinition
  (No actual instance created yet — just metadata)
        │
        ▼
When the first bean requests ProductFeignClient injection:
  FeignClientFactoryBean.getObject() is called
        │
        ▼
FeignClientFactoryBean builds a Feign.Builder with:
  ┌─────────────────────────────────────────────────────────┐
  │ SpringMvcContract    — parses @GetMapping, @PathVariable │
  │ SpringEncoder        — serializes @RequestBody via Jackson│
  │ SpringDecoder        — deserializes response via Jackson  │
  │ FeignErrorDecoder    — maps non-2xx to domain exceptions  │
  │ FeignBlockingLoadBalancerClient — lb:// → Eureka lookup   │
  └─────────────────────────────────────────────────────────┘
        │
        ▼
ReflectiveFeign.newInstance(target)
  — builds SynchronousMethodHandler for each method
  — calls Proxy.newProxyInstance()
        │
        ▼
JDK Dynamic Proxy implementing ProductFeignClient
  — injected as a Spring bean wherever @Autowired ProductFeignClient
```

**Key class names to know for interview:**

- `FeignClientsRegistrar` — the scanner
- `FeignClientFactoryBean` — the factory that produces the proxy
- `ReflectiveFeign` — builds the handler map
- `FeignInvocationHandler` — the `InvocationHandler` behind the proxy
- `SynchronousMethodHandler` — per-method handler that builds and fires the request

## 4. JDK Dynamic Proxy vs CGLIB

Two proxy mechanisms exist in the Spring/Java ecosystem. Feign uses **JDK Dynamic Proxy exclusively**.

| Aspect                        | JDK Dynamic Proxy                                                                  | CGLIB                                                            |
| ----------------------------- | ---------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| Works on                      | Java interface                                                                     | Concrete class (subclass)                                        |
| How                           | `Proxy.newProxyInstance()` → generates class implementing the interface at runtime | ASM bytecode generation → creates a subclass of the target class |
| Requires                      | Target must be an interface                                                        | Target must be a concrete class (or non-final)                   |
| InvocationHandler             | `java.lang.reflect.InvocationHandler`                                              | MethodInterceptor                                                |
| Used by Feign                 | Yes — Feign interfaces ARE interfaces                                              | No — there is no concrete class to subclass                      |
| Used by Spring @Transactional | When bean implements interface                                                     | When bean is a concrete class with no interface                  |
| Used by @Cacheable            | Same as @Transactional                                                             | Same as @Transactional                                           |

**Why Feign can only use JDK Dynamic Proxy:** There is no concrete `ProductFeignClientImpl` class — only the interface. CGLIB generates a subclass of a real class, which doesn't apply here. JDK Dynamic Proxy generates a class that _implements_ the interface — exactly what's needed.

**How JDK Dynamic Proxy works internally:**

```
Proxy.newProxyInstance(
    classLoader,
    new Class[]{ProductFeignClient.class},   // interfaces to implement
    feignInvocationHandler                    // handler for all method calls
)
```

The JVM generates bytecode for a class like:

```java
public final class $Proxy42 implements ProductFeignClient {
    public ProductDTO getProductById(Long id) {
        return (ProductDTO) handler.invoke(this, getProductByIdMethod, new Object[]{id});
    }
}
```

This class exists only in memory, never on disk.

## 5. Runtime Call Flow

Full debug-level trace for `productFeignClient.getProductById(42L)`:

```
1. Calling code:
   ProductDTO dto = productFeignClient.getProductById(42L);

2. JVM routes to JDK Dynamic Proxy → FeignInvocationHandler.invoke(proxy, method, args)

3. FeignInvocationHandler looks up SynchronousMethodHandler
   — one per method, stored in a dispatch Map<Method, MethodHandler>

4. SynchronousMethodHandler.invoke(args)
   — retrieves the RequestTemplate for this method:
     template: PUT /api/products/{id}/deduct-stock?quantity={quantity}

5. Fills path variables and query params:
   template expanded: GET /api/products/42

6. Passes RequestTemplate to FeignBlockingLoadBalancerClient

7. FeignBlockingLoadBalancerClient queries Eureka LoadBalancer:
   — asks for an instance of "PRODUCT-SERVICE"
   — Eureka returns: [localhost:8089, ...]
   — LoadBalancer selects: localhost:8089 (round-robin or configured strategy)

8. Substitutes base URL:
   final URL: http://localhost:8089/api/products/42

9. Makes a blocking HTTP GET (Apache HttpClient or OkHttp under the hood)

10. Response: HTTP 200 OK, body = {"id":42,"name":"iPhone","price":999.99,"stockQuantity":5,...}

11. FeignDecoder.decode(Response response, Type type)
    — wraps response body as InputStream
    — SpringDecoder delegates to Jackson ObjectMapper.readValue(inputStream, ProductDTO.class)

12. Jackson deserializes:
    — sees FAIL_ON_UNKNOWN_PROPERTIES = false (Spring Boot default)
    — maps: id→42, name→"iPhone", price→999.99, stockQuantity→5, brandId→1, active→true
    — fields in JSON that aren't in ProductDTO: silently dropped
    — fields in ProductDTO with no JSON match: null/0/false (default values)

13. SynchronousMethodHandler returns ProductDTO to FeignInvocationHandler

14. FeignInvocationHandler returns ProductDTO to calling code
```

**What happens if the call fails at step 9 (connection refused)?**
Feign throws `RetryableException` → if retry is configured, retries up to N times → eventually throws `FeignException` subclass.

**What happens if step 10 returns HTTP 409 (Conflict)?**
FeignBlockingLoadBalancerClient receives the response → passes to `FeignErrorDecoder.decode()` → maps 409 → throws `InsufficientStockException` before step 11 executes.

## 6. DTO Projection

### The Problem it Solves

Product-service's full `ProductResponse` has 12 fields. Order-service only needs 4 of them. Portfolio-service needs 6. If all services used the full `ProductResponse`:

1. They'd all depend on `product-service` at compile time — tightly coupled.
2. Any field added to `ProductResponse` requires rebuilding every consumer.
3. Network payload is larger than needed.

### How it Works

Spring Boot globally sets `DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES = false`.

When Jackson deserializes `{"id":1,"name":"iPhone","price":999.99,"stockQuantity":5,"brandId":7,"sku":"AP-001","description":"...","imageUrl":"...","categoryId":3,"categoryName":"Electronics","brandName":"Apple","active":true}` into `ProductDTO(Long id, String name, BigDecimal price, Integer stockQuantity, Long brandId, boolean active)`:

| JSON field    | ProductDTO field | Result           |
| ------------- | ---------------- | ---------------- |
| id            | id               | Mapped           |
| name          | name             | Mapped           |
| price         | price            | Mapped           |
| stockQuantity | stockQuantity    | Mapped           |
| brandId       | brandId          | Mapped           |
| active        | active           | Mapped           |
| sku           | (none)           | Silently dropped |
| description   | (none)           | Silently dropped |
| imageUrl      | (none)           | Silently dropped |
| categoryId    | (none)           | Silently dropped |
| categoryName  | (none)           | Silently dropped |
| brandName     | (none)           | Silently dropped |

The 6-field `ProductDTO` is populated correctly. The extra 6 fields are gone. No error.

### Failure Cases

```
Scenario: JSON has field, target has field          → Mapped normally
Scenario: JSON has field, target lacks field        → Silently dropped (FAIL_ON_UNKNOWN=false)
Scenario: Target has field, JSON lacks field        → null / 0 / false (Java default)
Scenario: Incompatible types (String → BigDecimal)  → MismatchedInputException at runtime
```

### Pattern Name: DTO Projection

Each consuming service declares a minimal DTO with only the fields it needs. This is the same pattern as JPA projections (interface-based or record-based) — project only what you query.

## 7. FeignErrorDecoder

### Default Feign Behavior (Without Custom Decoder)

For any non-2xx response, Feign throws a `FeignException` subclass:

- 400 → `FeignException.BadRequest`
- 404 → `FeignException.NotFound`
- 409 → `FeignException.Conflict`
- 500 → `FeignException.InternalServerError`

These are library types. They carry no domain meaning. Catching `FeignException.Conflict` in business code couples your service to the HTTP transport layer.

### FeignErrorDecoder

`ErrorDecoder` is a Feign interface with a single method:

```
Response decode(String methodKey, Response response) → Exception
```

The decoder receives the raw `Response` object **before** the default exception is thrown. It can inspect the status code, read the body, and throw a domain-specific exception.

**EquityCart `FeignErrorDecoder` in commons:**

```
HTTP 409 from PRODUCT-SERVICE /api/products/{id}/deduct-stock
       ↓
FeignErrorDecoder.decode("ProductFeignClient#deductStock", response)
       ↓
switch(status):
  case 409 → throw new InsufficientStockException("Insufficient stock")
  case 404 → return new Default().decode(methodKey, response)  // FeignException.NotFound
  default  → return new Default().decode(methodKey, response)
       ↓
InsufficientStockException propagates up to OrderServiceImpl.placeOrder()
       ↓
GlobalExceptionHandler maps InsufficientStockException → 409 Conflict HTTP response
```

### Registration

`@Component` on the decoder causes Spring to wire it into **every** Feign client in the context automatically. No explicit registration needed. All clients share the same error decoder unless you specify `configuration = MyConfig.class` on specific `@FeignClient`.

### What FeignErrorDecoder Cannot Do

**Cannot intercept 200-but-failure responses.** The decoder only fires on non-2xx. Some APIs return HTTP 200 with a `{success: false, error: "..."}` body. Three approaches for that case:

1. **Envelope return type**: Change return type to `ApiResponse<ProductDTO>`, check `.isSuccess()` in calling code.
2. **Custom Decoder**: Implement `Decoder` interface, inspect the body before returning (fires on all responses including 200).
3. **ResponseInterceptor (Feign 12+)**: Post-execution hook that can inspect any response.

## 8. @RequestParam vs @RequestBody in Feign

### @RequestParam — Query Parameter or Form Parameter

`@RequestParam("quantity") int quantity` maps `quantity` as a URL query parameter: `?quantity=5`.

**Use when:**

- Single scalar value
- Primitive or simple type (int, String, Long, boolean)
- No need for a JSON body
- HTTP GET or PUT without a structured payload

```java
@PutMapping("/api/products/{id}/deduct-stock")
void deductStock(@PathVariable("id") Long id, @RequestParam("quantity") int quantity);
// HTTP: PUT /api/products/42/deduct-stock?quantity=5
// Body: (none)
```

### @RequestBody — JSON Payload

`@RequestBody UpdateOrderStatusRequest request` serializes `request` to JSON and puts it in the HTTP request body.

**Use when:**

- Structured multi-field input
- Complex type (a DTO/record with multiple fields)
- POST, PUT, or PATCH with a domain object

```java
@PatchMapping("/api/order/{orderId}/status")
void updateOrderStatus(@PathVariable("orderId") Long orderId,
                       @RequestBody UpdateOrderStatusRequest request);
// HTTP: PATCH /api/order/7/status
// Body: {"status":"CONFIRMED"}
```

### Rule

> Single scalar → `@RequestParam`. Structured input → `@RequestBody`.

**What happens if you use @RequestBody for a scalar?**
Feign wraps the single int in a JSON body (`5` or `{"quantity":5}` depending on how it's interpreted). The server may reject this with 415 Unsupported Media Type or 400 Bad Request if it expects a query parameter.

**What happens if you omit the annotation entirely on a non-path param?**
Feign defaults to treating it as a query parameter for primitive types in GET requests, but behaviour is ambiguous for non-GET methods. Always be explicit.

## 9. Load Balancing via Eureka

### The `lb://` URI Scheme

When you specify `@FeignClient(name = "PRODUCT-SERVICE")`, Spring Cloud translates this to the URI `lb://PRODUCT-SERVICE` internally. The `lb://` prefix signals to the `FeignBlockingLoadBalancerClient` wrapper that service discovery should resolve the actual host.

### Resolution Flow

```
productFeignClient.getProductById(42L)
       ↓
FeignBlockingLoadBalancerClient intercepts the call
       ↓
Calls Spring Cloud LoadBalancer → queries EurekaClient
       ↓
EurekaClient returns a list of registered instances for "PRODUCT-SERVICE":
  - localhost:8089 (UP)
       ↓
LoadBalancer selects an instance (RoundRobin by default)
       ↓
Replaces lb://PRODUCT-SERVICE with http://localhost:8089
       ↓
HTTP request fires: GET http://localhost:8089/api/products/42
```

### What if PRODUCT-SERVICE is not registered?

`FeignBlockingLoadBalancerClient` throws `IllegalStateException: No instances available for PRODUCT-SERVICE`. This propagates as a `RetryableException` → if retries configured, retried → eventually `FeignException`.

**Implication for startup order:** If portfolio-service starts before product-service registers in Eureka, the first call will fail. Startup order matters: Config Server → Eureka → product-service → portfolio-service.

### Multiple Instances (Horizontal Scaling)

If product-service runs on two pods: localhost:8089 and localhost:9089, the load balancer rotates between them. No change needed in portfolio-service. This is the power of service discovery — the caller doesn't know or care how many instances exist.

## 10. Circular Dependency Constraint

### Why OrderFeignClient Cannot Live in Commons

```
commons module contains:
  - BaseEntity, GlobalExceptionHandler, KafkaConsumerConfig
  - ProductFeignClient (points to PRODUCT-SERVICE)
  - BrandTickerMappingDTO, ProductDTO (used by ProductFeignClient)

order-service depends on:
  - commons (for BaseEntity, GlobalExceptionHandler, etc.)

If we put OrderFeignClient in commons:
  commons would need → order-service DTO types (OrderResponse, UpdateOrderStatusRequest)
  order-service depends on → commons
  RESULT: commons → order-service → commons  [CIRCULAR DEPENDENCY]
```

Gradle cannot build a project with circular dependencies. The build fails.

### Why ProductFeignClient CAN Live in Commons

```
commons does NOT depend on product-service
product-service depends on commons (for BaseEntity)
ProductFeignClient uses ProductDTO (lives in commons, no product-service import)
ProductFeignClient uses BrandTickerMappingDTO (lives in commons, no product-service import)
RESULT: No circularity — commons → (nothing), product-service → commons
```

### The Solution: Module Ownership

The rule: **A Feign client must live in the module that consumes it, unless the DTO types it uses live in commons.**

| Feign Client         | Lives in         | Why                                                                                                             |
| -------------------- | ---------------- | --------------------------------------------------------------------------------------------------------------- |
| `ProductFeignClient` | commons          | `ProductDTO` and `BrandTickerMappingDTO` are in commons; no circular dependency                                 |
| `OrderFeignClient`   | portfolio module | `OrderResponse`, `UpdateOrderStatusRequest` are in order-service; moving to commons creates circular dependency |

## 11. EquityCart Design Decisions (Step 10)

### Decision 1: product-service as dual-artifact (bootJar + jar)

`build.gradle` for product-service:

```
plugins { id 'org.springframework.boot' }
jar { enabled = true }                           // library jar (no manifest)
bootJar { archiveClassifier.set('exec') }        // executable jar with classifier
```

**Why:** Order-service and portfolio-service needed to compile against `project(':product-service')` during the migration. A `bootJar` cannot be used as a library dependency (it has `BOOT-INF/classes/` nesting). Enabling `jar` produces the flat artifact; `bootJar` still produces the executable.

**After full migration:** Once all consumers use Feign (no more `project(':product-service')`), remove `jar { enabled = true }` and the `archiveClassifier`. Let it be a pure executable.

### Decision 2: Pessimistic lock ownership belongs to product-service

`SELECT FOR UPDATE` on the product table can only be executed by the service that owns that database. When order-service called `productRepository.findByProductId(id)` directly, it held the lock. After extraction, order-service calls `productFeignClient.deductStock(id, qty)` via HTTP. The HTTP call enters product-service, which then acquires `SELECT FOR UPDATE` within its own transaction.

The lock still works correctly — it just now lives in the right place. The distributed transaction limitation is that the lock is released when the product-service transaction commits, independently of the order-service transaction. See `microservice-patterns.md §7.12` for full analysis.

### Decision 3: @EnableJpaRepositories kept for com.equitycart.order in portfolio-service

`SagaOutboxWriter` injects `OutboxEventRepository` (from order-service package). This is a JPA repository interface — no service beans, no Feign dependencies. Removing it from `@EnableJpaRepositories` removes the proxy registration, breaking `SagaOutboxWriter`.

The entity class `OutboxEvent` is in `com.equitycart.order.entity`. Portfolio-service manages this entity (and its `outbox_events` table) in its own `equitycart_portfolio` database. This is "shared entity class, separate database table" — a known transitional pattern during microservice extraction. The long-term fix is to create `com.equitycart.portfolio.outbox.SagaOutboxEvent` (portfolio-owned entity) and migrate `SagaOutboxWriter` to use it.

### Decision 4: @ComponentScan removal from com.equitycart.order

The root cause of the startup failure was that `@ComponentScan("com.equitycart.order")` loaded `OrderServiceImpl` as a Spring bean. After Step 10, `OrderServiceImpl` injects `ProductFeignClient` — which is only registered if `@EnableFeignClients` covers the right package. `@EnableFeignClients` in portfolio-service didn't cover the order-service JAR's feign package, so `ProductFeignClient` was never registered, so `OrderServiceImpl` couldn't be wired.

Fix: remove `"com.equitycart.order"` from `@ComponentScan`. The service beans (OrderServiceImpl, CartServiceImpl) are no longer needed in portfolio's context — all order operations now go through `OrderFeignClient` HTTP calls.

## 12. Interview Questions

**Q: What is the difference between RestTemplate and OpenFeign?**
RestTemplate is an imperative HTTP client — you write URLs, methods, headers, and response mapping by hand for each call. OpenFeign is declarative — you define an annotated interface, and Spring generates the implementation at startup via JDK Dynamic Proxy. Feign treats the HTTP contract as a Java interface contract.

**Q: What proxy mechanism does Feign use and why?**
JDK Dynamic Proxy. CGLIB generates subclasses of concrete classes. Feign only has an interface, no concrete class to subclass. JDK Dynamic Proxy generates a class at runtime that implements the interface and routes all method calls to an InvocationHandler.

**Q: Trace a Feign method call from application code to HTTP response.**
Call routes through JDK Dynamic Proxy → FeignInvocationHandler.invoke() → SynchronousMethodHandler → RequestTemplate built and filled → FeignBlockingLoadBalancerClient queries Eureka → selects instance → HTTP request fires → response returned to SynchronousMethodHandler → SpringDecoder invokes Jackson deserialization → calling code receives the return type.

**Q: What does @EnableFeignClients do at startup?**
Imports FeignClientsRegistrar which scans the specified basePackages for @FeignClient interfaces. For each found, registers a FeignClientFactoryBean bean definition. When a Feign client bean is first requested, FeignClientFactoryBean.getObject() builds Feign.Builder with encoder/decoder/contract/error-decoder/load-balancer and calls ReflectiveFeign.newInstance() → JDK Dynamic Proxy created and registered as the bean.

**Q: Why can a 12-field JSON response successfully deserialize into a 6-field DTO?**
Spring Boot sets Jackson's FAIL_ON_UNKNOWN_PROPERTIES to false globally. Jackson maps only the fields present in both the JSON and the target type; extra JSON fields are silently discarded. This is the DTO Projection pattern.

**Q: How does FeignErrorDecoder work and what can't it do?**
FeignErrorDecoder.decode() intercepts the Response object before Feign's default exception is thrown for any non-2xx response. It can read the status code and body and throw a domain exception. It cannot intercept 200 responses with failure bodies — for that you need a custom Decoder, an ApiResponse envelope return type, or Feign 12+ ResponseInterceptor.

**Q: Why does OrderFeignClient live in portfolio module and not commons?**
Commons cannot depend on order-service (order-service depends on commons — making commons → order-service would create a circular dependency). OrderFeignClient uses OrderResponse and UpdateOrderStatusRequest, both of which are order-service types. Therefore OrderFeignClient must live in portfolio module, which already has order-service as a Gradle dependency.

**Q: What's the difference between @RequestParam and @RequestBody in a Feign interface?**
@RequestParam maps the parameter as a URL query parameter (?key=value). Use for single scalar values (int, String, Long). @RequestBody serializes the parameter as a JSON body. Use for structured multi-field input (DTOs/records). Rule: single scalar → @RequestParam, structured input → @RequestBody.

**Q: What happens if the target service (lb://PRODUCT-SERVICE) is not registered in Eureka when a Feign call is made?**
FeignBlockingLoadBalancerClient finds no instances → throws IllegalStateException: No instances available for PRODUCT-SERVICE → wraps in RetryableException → if retries configured, retried → if exhausted, FeignException propagates to calling code.

## 13. Feign Interceptor Pipeline — Authorization Propagation (Phase 8)

### How Feign Interceptors Are Auto-Registered

Any `@Component` implementing `feign.RequestInterceptor` is automatically discovered by Spring and injected into **every** `@FeignClient` in the application context. No per-client wiring needed.

```
Spring Context Initialization:
  1. ComponentScan finds all @Component RequestInterceptor beans
  2. FeignClientFactoryBean collects them into List<RequestInterceptor>
  3. Feign.Builder.requestInterceptors(list) registers all interceptors
  4. Every @FeignClient proxy gets the same interceptor chain
```

### Invocation Order in Feign Pipeline

```
Your code calls: productFeignClient.getProduct(123)
    │
    ▼
JDK Dynamic Proxy → FeignInvocationHandler.invoke()
    │
    ▼
SynchronousMethodHandler.executeAndDecode()
    │
    ├── Build RequestTemplate from method annotations
    │
    ├── for (RequestInterceptor interceptor : requestInterceptors) {
    │       interceptor.apply(template);  // EACH interceptor modifies the template
    │   }
    │
    │   Order of execution (EquityCart):
    │   1. FeignCorrelationInterceptor → adds X-Correlation-Id header from MDC
    │   2. FeignAuthorizationInterceptor → adds Authorization header from RequestContextHolder
    │
    ├── FeignBlockingLoadBalancerClient resolves lb://SERVICE-NAME → actual host:port
    │
    ├── HTTP request fires with ALL headers set by interceptors
    │
    └── Response decoded → returned to calling code
```

### FeignAuthorizationInterceptor — RequestContextHolder Mechanism

**Problem:** When order-service calls product-service via Feign, it creates a brand-new HTTP request. The user's original Authorization header is NOT automatically copied.

**Solution:** Read the header from the original request stored in `RequestContextHolder` (ThreadLocal):

```
Original HTTP request arrives → FrameworkServlet stores in ThreadLocal
    │
    │  [same thread continues through controller → feign call]
    │
    ▼
FeignAuthorizationInterceptor.apply(template):
    1. RequestContextHolder.getRequestAttributes()  → reads ThreadLocal
    2. Cast to ServletRequestAttributes
    3. .getRequest().getHeader("Authorization")     → extracts Bearer token
    4. template.header("Authorization", value)      → copies to outgoing request
```

**Critical constraint:** This ONLY works when the Feign call executes on the same thread that received the original HTTP request (synchronous servlet model). Breaks in:
- Kafka consumer threads (no originating HTTP request → RequestContextHolder returns null)
- @Async child threads (ThreadLocal does not propagate to new threads)
- @Scheduled threads (no originating HTTP request)

In null cases, the interceptor falls back to `ServiceTokenProvider.getServiceToken()` — generating a short-lived machine-identity JWT (subject=0, role=SERVICE, 60s expiry) so the downstream service still receives a valid Bearer token. This was added in Phase 8 after discovering that Kafka consumers calling Feign clients got 403 Forbidden.

### Two Interceptors, Two Concerns

| Interceptor                   | Reads from                                 | Writes to               | Survives across threads?                                |
| ----------------------------- | ------------------------------------------ | ----------------------- | ------------------------------------------------------- |
| FeignCorrelationInterceptor   | MDC ThreadContext (InheritableThreadLocal) | X-Correlation-Id header | YES — InheritableThreadLocal                            |
| FeignAuthorizationInterceptor | RequestContextHolder (plain ThreadLocal)   | Authorization header    | NO — plain ThreadLocal (fallback: ServiceTokenProvider) |

This difference is intentional: correlation IDs are lightweight tracing data safe to propagate anywhere; auth tokens are sensitive and should NOT leak to unrelated threads.

## Section 13: HTTP Client Transport — feign-hc5 and the PATCH Problem

### The Problem

OpenFeign's default HTTP transport is `java.net.HttpURLConnection` — a class from JDK 1.1 (late 1990s). It hardcodes supported methods as: GET, POST, PUT, DELETE, HEAD, OPTIONS, TRACE. The PATCH method (RFC 5789, 2010) was never added. Any `@PatchMapping` on a Feign interface throws:
```
java.net.ProtocolException: Invalid HTTP method: PATCH
```

### Why It Bites in EquityCart

`OrderFeignClient.updateOrderStatus()` uses PATCH — semantically correct (partial update of order status). Works fine in Postman and via direct controller testing, but fails when portfolio-service calls it through Feign.

### The Fix

```gradle
// portfolio/build.gradle (or any module using Feign with PATCH)
implementation 'io.github.openfeign:feign-hc5'
```

Spring Cloud OpenFeign auto-detects feign-hc5 on the classpath and replaces the default `HttpURLConnection` transport with Apache HttpClient 5. No `@Bean`, no configuration change — just the dependency.

### HTTP Client Evolution in Feign

| Dependency       | HTTP Client                | PATCH Support | Notes                                  |
| ---------------- | -------------------------- | :-----------: | -------------------------------------- |
| (none — default) | java.net.HttpURLConnection | ✗             | JDK built-in, ~1997                    |
| feign-httpclient | Apache HttpClient 4        | ✓             | Legacy, works fine                     |
| feign-okhttp     | OkHttp 3/4                 | ✓             | Popular, good HTTP/2                   |
| feign-hc5        | Apache HttpClient 5        | ✓             | Current recommendation                 |
| feign-java11     | java.net.http.HttpClient   | ✓             | JDK 11+, modern but less battle-tested |

### Interview Questions

**Q: "Your PATCH endpoint works with curl but fails through Feign — what's happening?"**
A: OpenFeign defaults to `HttpURLConnection` which predates RFC 5789 and doesn't support PATCH. The fix is adding `feign-hc5` — it replaces the transport with Apache HttpClient 5. Auto-configured by Spring Cloud OpenFeign; no code changes needed.

**Q: "Should you use PUT or PATCH for updating order status?"**
A: PATCH is semantically correct — you're modifying a single field (status), not replacing the entire resource. PUT implies sending the full resource representation. However, if your HTTP client can't handle PATCH (legacy systems), PUT is acceptable for single-field updates — pragmatism over purity.
